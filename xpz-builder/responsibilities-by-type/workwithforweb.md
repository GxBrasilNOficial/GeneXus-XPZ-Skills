# WorkWithForWeb — Responsibilities and Quality Checklist

Satellite of `xpz-builder/SKILL.md` for the `WorkWithForWeb` object type (`type="78cecefe-be7d-4980-86ce-8d6e91fba04b"`, `Object/@name` starts with `WorkWithWeb`). **Load this file end-to-end before generating, editing, or packaging a `WorkWithForWeb`**, in addition to the main `SKILL.md`.

## Responsibilities

### Structural form detection (Form A vs Form B)

WorkWithForWeb has two distinct XML structural forms depending on context. The 9-WW gate (`Test-GeneXusWorkWithWebApply.ps1`, invoked from WORKFLOW) handles detection automatically, but the agent must be aware of both forms when reasoning about a WorkWithForWeb:

- **Form A (packaging form)**: Part `babfa2b2-19a0-4ef1-b5f4-81b7c7be79dc` with `<Source><Properties>` containing `<Property><Name>Apply</Name>` and `<Property><Name>Transaction</Name>`. Used in `import_file.xml` packages and in XMLs generated from sanitized templates.
- **Form B (acervo form)**: Part `a51ced48-7bee-0001-ab12-04e9e32123d1` with `<Data Pattern="78cecefe-be7d-4980-86ce-8d6e91fba04b">` whose CDATA contains `<transaction transaction="<guid>-<TransactionName>" />`. Used in `ObjetosDaKbEmXml/WorkWithForWeb/*.xml` (materialized acervo).

In Form B, `Apply` is implicitly `True` by construction — a WorkWithForWeb materialized in the acervo was generated by the pattern; the `<Data Pattern="...">` element confirms the pattern is bound. The KbIntelligence index also materializes `is_generated_object`/`pattern_object_id`/`instance_key` on the `objects` table for a deterministic generated-vs-authored check (query `object-info`; filter `--generated`/`--authored`; see `xpz-index-triage/SKILL.md`).

### Generated Views and URL calls (GX18)

The observed generation chain is `WorkWithWeb<Trn>` → `WW<Trn>` (Selection) → `View<Trn>` → `<Trn>General` (Tabular) and `<Trn><Code>WC` (Grid). A standard pattern-generated `View<Trn>` does not materialize its own body in the XML. In the measured slice, 183 of 184 `View*.xml` files had no `<Source>`; the one exception was a customized View. Its observed call signature is the base Transaction keys in declared order, followed by a final string tab selector `code`; child-level keys are excluded. Pass `""` to request the default tab. Use the tab's `code`, not its display `name` or `wcname`.

The default-tab comparison in generated C# varied by generation date: older Views compared `"General"`, while later regenerated Views compared `"Geral"`, despite there being no tab with `code="Geral"`. Do not pass either literal to request the default tab; pass `""`. For a non-default tab, use its effective `code`. This is a dated generator quirk, not a contract to use the display `name`.

The `View` is not a Web Component (`WEB_COMP`); do not embed it through a `<component>`. Access it by URL (`.Call`, `.Link`, or the generated link flow). In the inspected corpus, `<component>` used `.Object = <Obj>.Create(...)` for Web Components, while `<embeddedpage>` used `.Source = <Obj>.Link(...)` for other embeddable objects. The separate `webObject="..."` form was observed only in GAM and does not make a generated `View` embeddable. A `View` rejected as a component produced `spc0045` in a completed GX18 build. See [01j-workwithweb-cdata-padroes.md](../../01j-workwithweb-cdata-padroes.md) for the aggregated `wcname` exception and the stable tab selector.

| Grid `wcname` exceptions | Count | Reading rule |
|---|---:|---|
| `wcname` follows the referenced Transaction rather than the Grid tab's `code` | 14 | Keep using `code` as the URL tab selector; do not derive it from `wcname` |

### CDATA editing rules

When editing the CDATA payload of a WorkWithForWeb (typically Form B), load [01j-workwithweb-cdata-padroes.md](../../01j-workwithweb-cdata-padroes.md) first. The internal XML has at minimum two distinct `<actions>` scopes and often more when Grid tabs are present — empirically, 2/3 of objects in production KBs have `<actions>` in both `<selection>` (list-level) and `<tab>` (detail/grid-level).

- Do not use broad text substitution over repeated tags such as `<actions>`; a pattern-only regex will match across all levels: `<selection>/<actions>` (list actions), `<tab type="Tabular">/<actions>` (per-record actions), and each `<tab type="Grid">/<actions>` (child grid actions).
- Anchor any textual insertion at the intended scope using the parent block's unique structural identifier: `<selection>` for list-level actions; `<tab code="General">` for the main Tabular detail tab; `<tab code="X">` for a specific Grid tab — the `code` attribute is the stable KB-side identifier generated by the pattern and does not vary by locale.
- Confirm any new action appears exactly once in the intended scope; duplicates or ambiguous action scope block packaging.

## Quality Checklist

- [ ] When calling a generated `View`, only base Transaction keys in order and the final string `code` selector were supplied; child keys were excluded, `""` was used for the default tab, and `name`/`wcname` were not substituted for `code`
- [ ] A generated `View` was accessed by URL rather than embedded as a `<component>`; the `wcname` Grid exceptions were treated as labels/names, not selectors
- [ ] For `WorkWithForWeb` action changes, [01j-workwithweb-cdata-padroes.md](../../01j-workwithweb-cdata-padroes.md) was loaded; the target scope was anchored by its unique structural identifier (`<selection>`, `<tab code="General">`, or `<tab code="X">`) and the new action appears exactly once in that scope
